# GoLe-metrics

GoLe 팀의 **전달 지표**를 주기적으로 찍어 쌓는 곳.

우리는 셋 다 클로드 코드·코덱스로 개발한다. 그게 실제로 효과가 있는지에 대해
**심증은 있는데 물증이 없었다.** 이 저장소는 그 물증을 만들려는 시도다.

## 먼저, 이 저장소가 답하지 않는 것

**"AI 가 우리를 더 빠르게 하는가"에는 답할 수 없다.** 대조군이 없기 때문이다.
"AI 없이 했으면 얼마나 걸렸을까"를 알려면 평행우주가 필요하고, 팀이 3명인 한
그 답은 영원히 나오지 않는다. 남의 RCT 도 다른 코드베이스·다른 사람이라 그대로 옮겨오지 못한다.

그리고 그 질문은 **생각보다 위험하다.** METR 이 2025년에 경험 많은 오픈소스
개발자들로 RCT 를 돌렸더니, AI 도구를 쓴 쪽이 **19% 느렸는데 본인들은 20% 빨라졌다고
느꼈다.** 체감이 실제와 반대로 나온 것이다. 자기 생산성에 대한 느낌은 증거가 아니다.

> 숫자는 직접 확인해라. 이 저장소는 남의 연구를 인용하려고 만든 게 아니라
> **우리 데이터를 쌓으려고** 만들었다.

## 그래서 대신 답하는 것

| 증명 불가 | 이 저장소가 답하는 것 |
|---|---|
| AI 가 우리를 더 빠르게 하는가 | 우리가 만든 하네스가 제 역할을 하는가 |
| AI 없이 했으면 얼마나 걸렸을까 | 에이전트 결과물이 얼마나 자주 그대로 서는가 |
| TDD 가 의미 있는가 | 우리 테스트가 실제로 무엇을 잡았는가 |
| 우리가 효율적인가 | 어떤 PR 이 비쌌고, 비싼 PR 이 더 잘 버텼는가 |

오른쪽은 대조군이 필요 없다. 절대적 기준 없이도 **추세**를 보면 되고,
나빠지면 그 자체가 신호다.

## 쓰는 법

```bash
python3 collect.py                 # 리포트와 JSON 스냅샷 생성
python3 collect.py --by-author     # 개인별 분해 (화면에만, 저장하지 않는다)
python3 collect.py --repo owner/name --pr-limit 300
python3 collect.py --vault ../GoLe-obsidian   # 빠져나간 결함 집계 (기본으로 옆 디렉터리를 찾는다)
python3 collect.py --no-sessions   # 세션 로그를 읽지 않는다 (투입 칸을 비운다)
python3 collect.py --self-test     # 집계 로직 자체 검증 (gh·네트워크 불필요)
```

의존성은 `python3`(표준 라이브러리만)과 로그인된 `gh` CLI 뿐이다.

- `reports/YYYY-MM-DD.md` — 사람이 읽는 스냅샷
- `data/YYYY-MM-DD.json` — 기계가 읽는 원본

**개인별 수치는 커밋하지 않는다.** 이 저장소는 공개이고, 개인 생산성 비교는
지표의 목적이 아니다. 필요하면 `--by-author` 로 로컬에서만 본다.

## 재는 것

| 지표 | 무엇을 보는가 |
|---|---|
| 재작업률 | 머지 후 7일 내 같은 파일을 `fix`/`revert` 가 다시 건드린 PR 비율 |
| CI 첫 시도 통과율 | 브랜치의 첫 CI 실행이 바로 성공한 비율 |
| 브랜치당 CI 실행 횟수 | CI 를 시행착오 도구로 쓰고 있는 정도 |
| 머지까지 걸린 시간 | PR 열림 → 머지 |
| PR 크기 | 중앙값·p90·최대. 검토 가능성의 상한 |
| 리뷰율 | GitHub 공식 리뷰가 달린 PR 비율 |
| 봇 비중 | dependabot 이 흐름에서 차지하는 몫 |
| 릴리스 빈도 | CalVer 태그 간격. main 푸시 + CI 성공 시 자동 생성된다 |
| 빠져나간 결함 | 볼트 `07_이슈기록` 의 운영 이슈 / 릴리스 수 |
| 에이전트 투입 | 세션 로그의 활성 시간·출력 토큰. PR 단위로 귀속된다 |
| 투입 대 재작업 | 재작업된 PR 과 아닌 PR 의 투입 차이 |

각 지표의 한계는 `collect.py` 의 docstring 과 리포트 JSON 의 `주의` 필드에 적혀 있다.
**숫자만 보고 결론 내리지 마라.**

## 분모 — 에이전트 투입

여기 있는 지표는 오랫동안 전부 **비율**이었다. 재작업률·통과율·리뷰율은 "결과물이
얼마나 버티나"를 보지만, **"얼마가 들었나"** 는 아무도 안 세고 있었다.
효율 = 산출 ÷ 투입인데 분모가 통째로 비어 있었다는 뜻이다.

그 분모는 새로 계측할 게 없었다. 에이전트 CLI 가 이미 로컬에 세션 로그를 남긴다.

```
~/.claude/projects/**/*.jsonl    timestamp · usage · gitBranch · pr-link
~/.codex/sessions/**/*.jsonl     timestamp · cwd · token_count
```

`gitBranch` 로 PR 브랜치에 붙이고, 안 붙는 세션은 `pr-link` 레코드로 보충한다.
그래서 **"이 PR 에 에이전트 시간이 몇 시간 들었나"** 가 나온다.

**본문은 읽지 않는다.** 프롬프트·응답 내용은 건드리지 않고 타임스탬프·토큰·브랜치·
PR 번호만 본다. 저장소가 공개이므로 커밋되는 것도 집계값뿐이다.

### 한계가 크다. 반드시 같이 읽어라

- **기계 한 대의 로그다.** 세션 로그는 로컬에만 있다. 팀 전체를 보려면 셋 다 각자
  자기 기계에서 돌려야 한다. 지금 숫자는 팀 투입이 아니라 **하한선**이다.
- **사람 시간은 안 잡힌다.** 오르카에서 눈으로 검토한 시간, 손으로 테스트한 시간,
  고민한 시간은 로그에 없다.
- **유휴 15분 임계값은 임의다.** 바꾸면 숫자가 통째로 움직인다. 절대값이 아니라 추세로 봐라.
- **Codex 는 PR 에 못 붙는다.** 브랜치를 안 남기고 `cwd` 만 남겨서 총량에만 들어간다.
- **커버리지를 먼저 봐라.** 세션 로그가 붙은 PR 비율이다. 낮으면 아래 비교는 아무 말도 못 한다.

### CI 에서는 비어 있다

러너에는 세션 로그가 없다. 그래서 매주 월요일 자동 실행은 이 칸을 비우고,
**직전 스냅샷 값을 이어받는다** — 안 그러면 로컬에서 채운 값이 매주 지워진다.
(빠져나간 결함이 볼트 때문에 같은 문제를 겪어서 이미 있던 장치를 확장했다.)

## 재지 않는 것

`docs/측정 원칙.md` 에 이유와 함께 적어 두었다. 요약하면 — **squash merge 와 TDD 자체는
측정하지 않는다.** 전자는 생산성이 아니라 가독성 선택이고, 후자는 20년간 메타분석이
엇갈린 문제라 3명 데이터로 판정될 수 없다.

## 자동화

`.github/workflows/weekly.yml` 이 매주 월요일 09:00 KST 에 스냅샷을 찍어 커밋한다.

**PAT 은 필요 없다.** GoLe 은 공개 저장소라 PR·Actions 이력을 `GITHUB_TOKEN` 으로 읽는다.

예외가 하나 있다 — **빠져나간 결함**은 볼트(`GoLe-obsidian`, 비공개)를 읽어야 해서
CI 에서는 비어 있다. 로컬 실행에서는 옆 디렉터리를 자동으로 찾아 채운다.
CI 에서도 채우려면 볼트 읽기 권한이 있는 PAT 을 `secrets.METRICS_TOKEN` 에 넣어라.
없으면 그 칸만 `—` 로 남고 나머지는 정상으로 돈다.

## 지금까지 나온 것

2026-09-13, PR 82건 · CI 실행 300건 · 릴리스 1건 기준.

- 재작업률 **41%** — 열에 넷이 7일 안에 같은 파일을 다시 고쳤다
- 리뷰율 **0%** — GitHub 공식 리뷰가 달린 PR 이 한 건도 없다
- 머지까지 중앙값 **0.2시간** (12분)
- CI 첫 시도 통과율 **83%**, 브랜치당 CI 실행 중앙값 **1.5회**
- 빠져나간 결함 **3건** (`07_이슈기록`) — 표본이 너무 작아 추세로 읽을 수 없다
- 에이전트 투입 **39시간 · 출력 8.8M 토큰** (기계 한 대, 2026-08-08~09-12)

세 숫자가 한 이야기를 한다. **리뷰 없이 12분 만에 머지하고, 41% 를 다시 고친다.**
검토 비용이 사라진 게 아니라 재작업으로 옮겨 간 것으로 보인다 — METR 연구에서
개발자들이 느려진 메커니즘과 같은 모양이다.

단, 이건 **한 시점의 스냅샷이고 인과가 아니다.** 같은 파일을 건드렸다고 반드시
앞 PR 때문은 아니다. 몇 주 쌓아서 추세를 봐야 말할 수 있다.

릴리스가 1건뿐이라 릴리스 관련 지표는 아직 의미가 없다. `release-tag.yml` 이
2026-09-12 에 main 에 들어갔으니 다음 릴리스부터 쌓인다.

### 투입을 붙여 보니 — 아직 판정 보류

재작업한 PR 과 아닌 PR 의 투입을 비교하려 했는데, **표본이 모자라 판정을 보류했다.**
그 과정에서 나온 것이 오히려 배울 점이다.

| | 표본 | 활성시간 중앙 | PR크기 중앙 |
|---|---:|---:|---:|
| 재작업됨 | 4 | 1.22h | 2,220줄 |
| 재작업 없음 | 9 | 0.32h | 146줄 |

**절단(censoring) 보정이 결론을 뒤집었다.** 재작업은 "머지 후 7일 안에 다시 고쳐졌나"라
지연 지표다. 어제 머지된 PR 은 고쳐질 시간이 없었을 뿐인데 기계적으로 "재작업 없음"으로
떨어진다. 보정 전에는 재작업한 PR 이 **더 짧게** 걸린 것처럼 보였고(0.47배),
관측 창이 안 닫힌 18건을 빼자 **3.81배**로 부호가 뒤집혔다.

그리고 그 3.81 도 **쓰지 않는다.** 작은 쪽 표본이 4건이라 중앙값이 한두 PR 에
좌우된다. 수집기가 `MIN_COMPARE_N` 미만이면 배수를 아예 안 내보낸다 —
숫자를 내보내면 반드시 결론처럼 읽히기 때문이다.

두 그룹의 **PR 크기가 15배 차이**라는 것도 같이 봐야 한다. 이 비교가 보고 있는 게
"투입 차이"가 아니라 "작업 크기 차이"일 수 있다. 교란을 통제하지 않았다.

몇 주 더 쌓여 양쪽 8건을 넘으면 그때 판정이 나온다.
