# 측정 원칙 — 무엇을 재고, 무엇을 재지 않는가

측정 비용은 **그것이 바꿀 결정의 크기에 비례해야 한다.** 거창한 지표 프로그램은
그 자체가 비용이고, 대개 아무 결정도 바꾸지 않는다.

## 측정할 것

전부 지금 데이터로 계산된다. 새로 심을 계측이 없다.

### 1. 재작업률

머지 후 7일 내에 같은 파일을 `fix`/`revert` 가 다시 건드린 PR 비율.

**에이전트 결과물이 실제로 버티는지를 보는 단일 최고 지표다.** 속도는 늘 좋아 보이지만
재작업은 숨지 않는다. 빨리 만들고 다시 고치면 여기서 드러난다.

한계: 같은 파일을 건드렸다고 반드시 앞 PR 탓은 아니다. 기능을 이어 만드느라 건드린 것도
잡힌다. 절대값이 아니라 **추세**로 봐라.

### 2. CI 첫 시도 통과율

브랜치의 첫 CI 실행이 바로 성공했는가.

에이전트가 처음 올린 게 그대로 서는 비율에 가장 가깝다. 낮으면 시행착오를 CI 에서
하고 있다는 뜻이다.

### 3. PR 당 CI 재실행 횟수

위의 비용 측면. 브랜치당 5회를 돌린다면 CI 는 검증 도구가 아니라 **디버거**로 쓰이고 있다.
나쁜 건 아니지만, 그렇다면 CI 가 못 잡는 종류의 결함은 아무도 안 보고 나간다는 뜻이기도 하다.

### 4. 빠져나간 결함

볼트 `07_이슈기록` 에 릴리스당 몇 건이 쌓이는가. **이건 자동으로 못 센다.** 이슈가 날 때마다
기록하는 습관이 있어야 지표가 된다. 없으면 0 이 나오는데, 그건 "결함이 없다"가 아니라
"기록하지 않았다"는 뜻이다.

### 5. 머지까지 걸린 시간

PR 열림부터 머지까지.

**짧다고 좋은 게 아니다.** 리뷰율·재작업률과 반드시 같이 봐라. 리뷰를 건너뛰면 이 숫자는
저절로 좋아지고, 비용은 재작업으로 옮겨 간다.

### 6. 리뷰율과 PR 크기

리뷰율은 GitHub 공식 리뷰만 센다. 오르카·대화로 본 것은 안 잡힌다.
그래서 0% 가 "아무도 안 봤다"는 뜻은 아니지만, **"기록이 남지 않았다"** 는 뜻이기는 하다.
기록이 없으면 나중에 원인을 추적할 수 없다.

PR 크기는 검토 가능성의 상한이다. 1,000줄 PR 은 사람이 검토했다고 말해도 실제로는
훑은 것이다. **에이전트는 큰 PR 을 아주 쉽게 만든다.**

### 7. 에이전트 투입 (분모)

세션 로그의 활성 시간·출력 토큰. **효율이라는 말을 쓰려면 반드시 있어야 하는 칸이다.**

1~6 은 전부 비율이다. 결과물이 얼마나 버티는지는 보이는데 얼마가 들었는지가 없었다.
대조군이 없어서 효율에 답을 못 한 게 아니라, **분모가 없어서** 못 했던 것이다.

이걸 붙이면 새로 답할 수 있는 질문이 생긴다 — "재작업률 41%" 는 30분짜리 PR 의 41% 와
8시간짜리 PR 의 41% 가 전혀 다른 이야기인데, 그 구분이 비로소 생긴다.

**여전히 "AI 가 우리를 빠르게 하는가"에는 답 못 한다.** 그건 대조군 문제라 분모로
풀리지 않는다. 답하는 건 "어떤 PR 이 비쌌나"까지다.

한계는 `README.md` 의 "분모 — 에이전트 투입" 에 적어 두었다. 요약하면 **기계 한 대의
하한선**이고, 사람이 검토·테스트한 시간은 안 잡힌다.

#### 여기서 배운 것 — 지연 지표는 절단을 걷어내야 한다

재작업은 "머지 후 7일 안에"가 조건이라 **관측 창이 닫혀야 값이 확정된다.** 어제 머지된
PR 을 그냥 "재작업 없음"에 넣으면 최근 PR 이 한쪽 그룹을 통째로 부풀린다.

실제로 이 보정 하나가 **결론의 부호를 뒤집었다** (0.47배 → 3.81배). 보정 전 숫자를
그대로 실었다면 정반대 처방이 나왔을 것이다. 지연 지표를 새로 만들 때마다 확인해라.

그리고 보정 후에도 표본이 4건이라 **배수를 내보내지 않기로 했다.** 숫자를 내보내면
"참고용"이라고 적어 둬도 결론처럼 인용된다. 수집기가 `MIN_COMPARE_N` 으로 막는다.

## 측정하지 말 것

### squash merge

**이건 생산성 문제가 아니라 가독성 선택이다.**

"squash 가 우리를 빠르게 하는가"는 측정해도 답이 안 나오고, 나와도 노이즈다.
트레이드오프가 이미 명확하다:

| | squash | merge commit |
|---|---|---|
| `git log main` | PR 하나 = 커밋 하나, 읽힌다 | 작업 커밋으로 가득 찬다 |
| dev ↔ main | 해시가 갈라져 **역병합이 필수** | 역병합 불필요 |
| 이등분 탐색 | 커밋 단위가 커서 범위가 넓다 | 세밀하다 |

볼트의 `02_아키텍처/03_인프라/Git 흐름과 릴리스 규약` 에 이 트레이드오프를 이미
정확히 적어 두었다. **그 수준이 적정선이다.** 더 파지 마라.

다만 **바꾸고 싶으면 바꿔도 된다.** 이건 데이터가 결정할 문제가 아니라 취향과 운영
편의가 결정할 문제다. 역병합(`chore(sync)`)이 반복적으로 귀찮다면 merge commit 으로
돌리는 게 합리적이고, 그 대가로 `main` 이력이 지저분해지는 걸 받아들이면 된다.
**어느 쪽도 "틀린" 선택이 아니다.** 판단 근거는 측정이 아니라 "우리가 `main` 이력을
얼마나 자주 읽는가"다.

### TDD 그 자체

"TDD 가 결함을 줄이는가"는 20년간 메타분석이 엇갈린 문제다. 효과 크기가 작고
연구 간 이질성이 크다. **팀 3명, 3개월 데이터로 판정될 문제가 아니다.**

대신 이걸 기록해라 — **"우리 테스트가 실제로 무엇을 잡았나."**

CI 가 빨간불을 낸 건마다 한 줄씩. 무엇이 잡혔고, 그게 프로덕션까지 갔으면 어땠을지.
반년 쌓이면 "E2E 가 값을 하는가"에 대해 남의 연구가 아니라 **우리 사례로** 말할 수 있다.
그건 통계가 아니라 증거 목록이고, 이 규모에서는 그쪽이 더 정직하다.

### 개인별 생산성

재지 않는다. 이 저장소는 공개이고, 사람 셋을 줄 세우는 건 지표의 목적이 아니다.
`--by-author` 는 로컬 디버깅용으로만 둔다.

## 가장 중요한 경고

**지표가 좋아지는 것과 사업이 되는 것은 다르다.**

성공 기준이 돈이라면, 개발 생산성은 **중간 변수**일 뿐 결과 변수가 아니다.
10배 빨리 만들고도 아무도 원하지 않는 걸 만들면 실패한다.

지금 GoLe 의 병목은 코드 생산 속도가 아닐 가능성이 높다 —
`GOLE_PRODUCTION_HOST_READY=false` 라 배포가 닫혀 있고, 운영 결제도 열리지 않았다.
**돈이 들어오는 경로 자체가 아직 없다.**

이 저장소의 숫자가 다 좋아져도 그 사실은 바뀌지 않는다. 지표는 "우리가 잘하고 있나"를
확인하는 도구지, "무엇을 해야 하나"를 알려주는 도구가 아니다.
